Setting up webhooks

Webhooks push events to your server the moment they happen, so you can stop polling for changes that may never come. Six steps take you from an empty route to an endpoint you can trust in production.

Build the endpoint

Start with a single route that accepts POST requests and nothing else. It needs no authentication of its own, because the request is authenticated by its signature rather than by a session, and adding a login in front of it is the most common reason a first webhook never arrives.

Read the request body as raw bytes before any middleware parses it. Signature verification runs over the exact bytes that were sent, and a JSON parser that reorders keys or normalises whitespace will produce a body that no longer matches the signature you were given.

Register the URL

Add the endpoint in your dashboard and subscribe it to the specific events you handle, not to everything. A subscription that fires on every event type in the catalogue means every future addition arrives at a handler that has no branch for it, and your logs fill with unknown types you cannot act on.

Register separate endpoints for test and live traffic. Sharing one URL across both makes it far too easy to act on a test event with production data, and the two streams are impossible to tell apart once they are interleaved in the same log.

Verify the signature

Every delivery carries a signature header computed from the raw body and a secret only the two of you hold. Recompute it on receipt and compare the two values with a constant-time comparison; a plain equality check leaks timing information that can be used to guess the signature byte by byte.

Signatures usually include a timestamp, and the timestamp is as important as the digest. Reject anything older than a few minutes so a captured request cannot be replayed later, and make sure the clock on your server is actually synchronised before you tighten that window.

Respond fast, work later

Return a 2xx status as soon as the signature checks out. Providers hold the connection open while you work and treat a slow response as a failure, so anything beyond writing the event to a queue or a table belongs in a background job rather than in the request.

That split also keeps your handler honest under load. When a batch of events arrives at once, a route that only records them stays fast regardless of how expensive the downstream work is, and the queue absorbs the burst instead of your web tier.

Retries and idempotency

Assume every event will arrive more than once. Retries after a timeout, a redelivery from the dashboard and an ordinary network hiccup all produce duplicates, and a handler that charges a card or sends an email on each one will do it twice.

Store the event id the first time you see it and treat a repeat as a no-op. Writing that record in the same transaction as the work itself is what makes the guarantee hold; two separate writes leave a window where the work is done and the record is not.

Monitoring and rotation

Log every delivery with its id, type and outcome, and alert on the failure rate rather than on individual failures. Providers disable an endpoint that fails for long enough, and the first sign is usually a quiet gap in the data rather than an error anyone noticed.

Rotate the signing secret on a schedule. Accept both the old and the new secret for the length of one rotation window, then drop the old one, so a delivery in flight during the change is still verified rather than rejected.
